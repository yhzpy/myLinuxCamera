## 1. 使用的系统与方式

本项目采用**极简的嵌入式 C 风格配置方案**，不包含任何运行时配置文件（如 .yaml/.json/.ini）、环境变量解析或特性开关框架。所有可配置项通过以下三种方式提供：
- **编译期宏**：集中在 `video2lcd/include/config.h`，用于定义全局调试开关和设备路径。
- **命令行参数**：主程序入口 `main.c` 通过 `argc/argv` 接收摄像头设备路径（如 `/dev/video0`）。
- **运行时探测**：LCD 分辨率、像素格式等由显示驱动在运行期查询（`GetDispResolution`），不依赖外部配置。

## 2. 关键文件

- `video2lcd/include/config.h`：唯一集中存放项目级配置宏的头文件。
- `video2lcd/main.c`：唯一消费配置的地方——解析 argv[1] 作为 V4L2 视频设备节点，并调用各模块初始化。
- `video2lcd/display/fb.c` 与 `video2lcd/display/disp_manager.c`：运行时从 framebuffer 设备获取 LCD 物理参数（宽、高、bpp），替代硬编码。
- `video2lcd/video/v4l2.c` / `video2lcd/video/video_manager.c`：根据传入的设备节点打开并查询摄像头能力。

## 3. 架构与设计约定

### 3.1 编译期配置（config.h）
`config.h` 仅暴露两个概念：
- `DBG_PRINTF`：调试输出宏，默认映射到 `printf`；注释掉后可关闭调试输出（典型嵌入式“零开销”开关）。该宏被 `main.c` 和各模块广泛使用。
- `FB_DEVICE_NAME`：Framebuffer 设备路径，当前硬编码为 `/dev/fb0`。

没有引入任何配置加载库（如 cJSON、libconfig、INI 解析器），保持二进制体积最小化，符合嵌入式资源受限场景。

### 3.2 命令行参数配置
`main.c` 对参数做最简校验：若 `argc < 2` 则打印用法并退出。唯一的配置入口是 `argv[1]`，即 V4L2 设备节点（如 `/dev/video0`）。无其他选项（无分辨率选择、无帧率设置、无缩放比例开关）。

### 3.3 运行时探测替代静态配置
对于可能随硬件变化的参数（LCD 分辨率、像素格式、每像素位数），项目选择在运行时通过 display 抽象层查询：
```c
GetDispResolution(&iLcdWidth, &iLcdHeight, &iLcdBpp);
```
这使得同一份固件可适配不同分辨率的 LCD 面板，无需重新编译。

### 3.4 模块间配置传递模式
配置以**结构体字段 + 函数参数**形式在各模块间传递，而非全局变量。例如 `T_VideoBuf`、`T_PixelDatas` 等结构体承载尺寸、bpp、行字节数等“配置态”数据，由上层初始化后逐层下发。

## 4. 约定与约束

- **设备路径必须通过编译期宏或命令行指定**：Framebuffer 路径写死在 `FB_DEVICE_NAME`，V4L2 设备路径必须通过命令行传入，不存在配置文件覆盖机制。
- **调试输出统一经 `DBG_PRINTF` 宏**：所有模块通过该宏输出日志，便于通过单一宏定义全局开关调试信息。
- **不支持运行时热更新配置**：由于没有配置加载器，修改任何配置（如切换设备、调整调试级别）均需重新编译或重启进程。
- **配置与业务逻辑解耦**：`config.h` 仅声明常量，业务逻辑通过函数接口（如 `DisplayInit`、`VideoDeviceInit`）间接使用，避免在业务代码中散落 `#define`。
- **无环境变量、无 feature flag、无 secrets 管理**：本项目未实现任何敏感信息或功能开关的配置机制。

## 5. 总结

这是一个典型的嵌入式 C 项目的轻量级配置体系：用 `#define` 处理编译期常量，用 `argv` 处理启动参数，用运行时 ioctl 探测硬件能力。其设计目标是**最小依赖、最小内存占用、最快启动**，适合资源受限的嵌入式 Linux 相机应用。若未来需要支持多设备、多分辨率、动态开关等功能，可在此基础上引入配置文件解析（如 INI）或环境变量读取。

# 04 · 格式转换模块深度拷打（YUV / MJPEG / RGB）

> 对应源码：`convert/convert_manager.c`、`convert/yuv2rgb.c`、`convert/mjpeg2rgb.c`、`convert/rgb2rgb.c`、`convert/color.c`、`convert/color.h`。

---

## Q1. 为什么需要格式转换？摄像头输出格式和 LCD 显示格式为什么不一样？

**参考答案：**

- **摄像头输出**通常是 YUV 系列（如 YUYV/YUV422）或压缩的 MJPEG。原因：
  - **YUV** 是符合人眼视觉特性的色彩编码——人眼对**亮度（Y）敏感、对色度（UV）不敏感**，所以 YUV422 让两个像素共享一组 UV，**采样率减半**，数据量比 RGB 小 1/3 左右，画质损失却几乎看不出来。传输/存储更高效。
  - **MJPEG** 是压缩格式，进一步减少数据量，适合带宽受限的 USB 传输。
- **LCD/framebuffer 显示**需要 RGB 格式（RGB565 或 RGB32），因为屏幕的每个像素点是由 R/G/B 三个子像素发光组成的，硬件直接驱动的是 RGB。

所以中间必须做**颜色空间转换**：把 YUV/MJPEG 解码/转换成 RGB，才能显示。

## Q2. YUV 和 RGB 是什么关系？讲讲 YUV422 的存储方式

**参考答案：**

YUV 和 RGB 是两种**颜色空间**，可以相互转换：
- **Y**：亮度（Luma），表示灰度明暗。
- **U、V**：色度（Chroma），表示颜色偏移（U = B-Y 蓝色差，V = R-Y 红色差）。

**YUV422（packed，即 YUYV）存储方式**：每 **4 个字节表示 2 个像素**，排列为 `[Y0 U0 Y1 V0]`：
- Y0、Y1：两个像素各自的亮度。
- U0、V0：两个像素**共享**的一组色度。

即：亮度每像素独立（4:2:2 里的第一个 4），色度水平方向每 2 个像素采样一次（2:2）。相比 YUV444（每像素独立 YUV），422 色度减半，省空间。

**命名规则**：`4:2:2` 表示以 4 像素宽、2 像素高的采样区域为单位，第一行采 4 个 Y、2 个色度，第二行复用色度。

## Q3. YUV→RGB 的转换公式是什么？你代码里怎么实现的？

**参考答案：**

标准转换公式（BT.601）：
```
R = Y + 1.4075 * (V - 128)
G = Y - 0.3455 * (U - 128) - 0.7169 * (V - 128)
B = Y + 1.7790 * (U - 128)
```
（U、V 减去 128 是因为它们的取值范围 0~255 中心在 128，代表无色度偏移。）

代码里在 `color.c` 用**查找表 + 宏**实现：
```c
#define R_FROMYV(y,v)   CLIP((y) + g_lutRv[(v)])
#define G_FROMYUV(y,u,v) CLIP((y) + g_lutGu[(u)] + g_lutGv[(v)])
#define B_FROMYU(y,u)   CLIP((y) + g_lutBu[(u)])
```
`g_lutRv[v]` 存的就是预先算好的 `1.4075*(v-128)`，运行时只需查表 + 整数加法。

**CLIP 宏**：
```c
#define CLIP(color) (unsigned char)(((color)>0xFF)?0xff:(((color)<0)?0:(color)))
```
把结果裁剪到 0~255，防止溢出（浮点系数运算结果可能超范围）。

## Q4. 为什么要用查找表（LUT）？性能提升在哪？

**参考答案（性能优化重点）：**

如果每个像素都用浮点公式计算：
```c
r = y + 1.4075 * (v - 128);   // 每像素多次浮点乘法
```
问题：
1. **浮点运算慢**，尤其在嵌入式 ARM（Cortex-A7 虽有 FPU，但浮点仍比整数慢）。
2. 一帧图像几十万像素，每像素 3 个分量都要算，**每帧上百万次浮点乘法**，实时视频根本扛不住。

**查找表优化**：`1.4075*(v-128)` 这类表达式，v 只有 0~255 共 **256 种取值**，结果也就 256 种。所以在初始化时（`initLut()`）**一次性把 256 个结果预先算好存进数组**：
```c
void initLut(void){
    for (i = 0; i < 256; i++){
        g_lutRv[i] = (int)(1.4075 * (i - 128));
        g_lutGu[i] = (int)(-0.3455 * (i - 128));
        g_lutGv[i] = (int)(-0.7169 * (i - 128));
        g_lutBu[i] = (int)(1.7790 * (i - 128));
    }
}
```
运行时把「浮点乘法」变成「**数组查表 + 整数加法**」：
```c
r = CLIP(y + g_lutRv[v]);   // 查表 + 加法，快得多
```

**空间换时间**的典型：用 4 个 256 元素的 int 数组（4KB）换来每像素几次浮点乘法的消除，实时性能大幅提升。

## Q5. Pyuv422torgb565 是怎么处理「两个像素共享 UV」的？

**参考答案（对应 yuv2rgb.c）：**

因为 YUV422 每 4 字节 = 2 像素，代码每次循环处理 2 个像素：
```c
size = image_width * image_height / 2;   // 循环次数 = 像素对数
for (i = size; i > 0; i--) {
    Y  = buff[0];   // 像素0 亮度
    U  = buff[1];   // 共享色度 U
    Y1 = buff[2];   // 像素1 亮度
    V  = buff[3];   // 共享色度 V
    buff += 4;      // 前进 4 字节

    // 像素0：用 Y + 共享的 U/V
    r = R_FROMYV(Y, V);  g = G_FROMYUV(Y, U, V);  b = B_FROMYU(Y, U);
    // 打包成 RGB565 写入 output

    // 像素1：用 Y1 + 同样的 U/V（共享）
    r = R_FROMYV(Y1, V); g = G_FROMYUV(Y1, U, V); b = B_FROMYU(Y1, U);
    // 打包成 RGB565 写入 output
}
```
关键：**U、V 被两个像素复用**，只有 Y 各自不同。这正是 YUV422 色度减半的体现。

RGB565 打包：
```c
r = r >> 3;  g = g >> 2;  b = b >> 3;         // 8位 → 5/6/5位
color = (r << 11) | (g << 5) | b;             // 拼成 16 位
*output_pt++ = color & 0xff;                  // 小端序：低字节先写
*output_pt++ = (color >> 8) & 0xff;
```

## Q6. MJPEG 是怎么解码的？讲讲 libjpeg 的调用流程

**参考答案（对应 mjpeg2rgb.c）：**

MJPEG 每一帧就是一个完整的 JPEG 图片，用 **libjpeg** 库解码，标准流程：

```c
struct jpeg_decompress_struct tDInfo;
tDInfo.err = jpeg_std_error(&tJerr.pub);       // 1. 设置错误处理
jpeg_create_decompress(&tDInfo);               // 2. 创建解压对象
jpeg_mem_src_tj(&tDInfo, 数据指针, 数据长度);    // 3. 设置数据源（内存）
jpeg_read_header(&tDInfo, TRUE);               // 4. 读 JPEG 头（拿到宽高、分量数）
tDInfo.scale_num = tDInfo.scale_denom = 1;     // 5. 缩放比 1:1（不解码时缩放）
jpeg_start_decompress(&tDInfo);                // 6. 开始解压
// 7. 逐行读取解压后的数据
while (tDInfo.output_scanline < tDInfo.output_height){
    jpeg_read_scanlines(&tDInfo, &aucLineBuffer, 1);   // 读一行（RGB888）
    CovertOneLine(宽, 24, 目标bpp, aucLineBuffer, pucDest);  // 转成目标格式
    pucDest += iLineBytes;
}
jpeg_finish_decompress(&tDInfo);               // 8. 完成解压
jpeg_destroy_decompress(&tDInfo);              // 9. 销毁对象释放资源
```

解码出来的是 **RGB888（24 位，每像素 R/G/B 各 1 字节）**，再通过 `CovertOneLine` 转成 LCD 需要的 RGB565 或 RGB32。

**为什么逐行处理**：`jpeg_read_scanlines` 一次读一行，边解码边转换，不用一次性把整张解码后的图存下来，**省内存**。

## Q7. libjpeg 的错误处理为什么要用 setjmp/longjmp？

**参考答案（难点，体现功底）：**

libjpeg 默认的错误处理函数 `error_exit` 在遇到致命错误（如数据损坏）时会**直接调用 `exit()` 终止整个程序**。这对一个实时视频程序是灾难——一帧坏数据就导致整个程序退出。

解决办法：**覆盖默认错误处理**，用 `setjmp/longjmp` 实现「非局部跳转」的错误恢复：
```c
typedef struct MyErrorMgr {
    struct jpeg_error_mgr pub;   // 标准错误管理器
    jmp_buf setjmp_buffer;       // 跳转恢复点
} T_MyErrorMgr;

static void MyErrorExit(j_common_ptr ptCInfo){
    // 格式化错误消息并打印
    longjmp(ptMyErr->setjmp_buffer, 1);   // 跳回 setjmp 处，而不是 exit
}

// 使用：
tDInfo.err = jpeg_std_error(&tJerr.pub);
tJerr.pub.error_exit = MyErrorExit;        // 替换错误处理函数
if(setjmp(tJerr.setjmp_buffer)){           // 设置恢复点
    // 出错时 longjmp 跳到这里 → 清理资源 → return -1
    jpeg_destroy_decompress(&tDInfo);
    free(aucLineBuffer);
    return -1;
}
// 正常解码流程...
```

**原理**：
- `setjmp(buf)` 保存当前执行环境（栈、寄存器等），第一次调用返回 0，走正常流程。
- 一旦 libjpeg 出错调用 `MyErrorExit` → `longjmp(buf, 1)`，程序**直接跳回 setjmp 的位置**，这次 setjmp 返回 1，进入错误处理分支，清理资源后正常返回，**程序不崩溃**，可以继续处理下一帧。

这是 C 语言里模拟「异常捕获」的经典手法，libjpeg 官方示例（example.c）就是这么做的。

## Q8. rgb2rgb 转换器有什么用？RGB565→RGB565 不是多此一举吗？

**参考答案（对应 rgb2rgb.c）：**

`rgb2rgb` 处理**摄像头直接输出 RGB565** 的情况，有两条路径：
- **RGB565 → RGB565**：摄像头格式和 LCD 格式都是 RGB565，**直接 memcpy**，不做像素运算。虽然看起来"没转换"，但它的意义是**统一处理流程**——让转换器框架有一个匹配项，主流程逻辑不用为"格式相同"写特例。而且拷贝这一步把数据从 mmap 采集缓冲区搬到显示缓冲区，本身也是必要的（不能直接在采集缓冲区上显示）。
- **RGB565 → RGB32**：摄像头输出 16 位，但 LCD 是 32 位，需要**逐像素扩展**：
  ```c
  r = color >> 11;  g = (color >> 5) & 0x3f;  b = color & 0x1f;   // 拆出 5/6/5 位
  color = ((r<<3)<<16) | ((g<<2)<<8) | (b<<3);   // 扩展回 8 位并拼成 0x00RRGGBB
  ```
  `r<<3` 是把 5 位补成 8 位（低位补 0），恢复成 8 位精度。

## Q9. convert_manager 是怎么自动选择正确的转换器的？

**参考答案（核心设计）：**

`convert_manager.c` 维护一个转换器链表，每个转换器有个 `isSupport(in, out)` 函数判断自己能不能处理某种格式对。

选择逻辑 `GetVideoConvertForFormats(in, out)`：
```c
PT_VideoConvert ptTmp = g_ptVideoConvertHead;
while (ptTmp){
    if (ptTmp->isSupport(iPixelFormatIn, iPixelFormatOut))  // 问每个转换器"你支持吗"
        return ptTmp;                                        // 第一个说支持的就返回
    ptTmp = ptTmp->ptNext;
}
return NULL;   // 没有匹配的
```

比如摄像头是 YUYV、LCD 是 RGB32：遍历到 yuv2rgb 转换器，它的 `isSupportYuv2Rgb(YUYV, RGB32)` 返回 1，就选中它。

这是**策略模式 + 责任链**的思想：每个转换器声明自己的能力（isSupport），管理器遍历查找匹配的。加新转换器只要注册进去，查找逻辑自动生效，无需改 `GetVideoConvertForFormats`。

`VideoConvertInit()` 里注册三个转换器：
```c
iError  = Yuv2RgbInit();      // 注册 yuv2rgb（并 initLut）
iError |= Mjpeg2RgbInit();    // 注册 mjpeg2rgb
iError |= Rgb2RgbInit();      // 注册 rgb2rgb
```

## Q10. T_VideoConvert 结构体为什么有个 ConvertExit？转换缓冲区内存怎么管理？

**参考答案：**

```c
typedef struct VideoConvert{
    char *name;
    int (*isSupport)(int in, int out);      // 判断是否支持
    int (*Convert)(in_buf, out_buf);        // 执行转换
    int (*ConvertExit)(out_buf);            // 释放转换分配的资源
    struct VideoConvert *ptNext;
} T_VideoConvert;
```

**ConvertExit 的作用**：释放 Convert 过程中 malloc 的输出缓冲区。因为转换器内部会为输出分配内存：
```c
if (!ptPixelDatasOut->aucPixelDatas)
    ptPixelDatasOut->aucPixelDatas = malloc(ptPixelDatasOut->iTotalBytes);
```
需要一个配对的释放函数，遵循「谁分配谁负责提供释放接口」的原则。

**内存管理的关键技巧（防重复分配）**：注意 `if (!aucPixelDatas)` 这个判断——只有指针为 NULL 时才 malloc。主循环里每帧都调 Convert，但因为输出缓冲区 `tConvertBuf` 在循环外 memset 成 0（指针 NULL），**第一帧 malloc，之后帧因为指针非空就跳过 malloc，复用同一块内存**。这样避免了「每帧 malloc/free」的频繁内存操作和潜在泄漏，是性能优化的细节。

**⚠️ 可改进点**：本项目主循环是 while(1) 死循环，实际没调用 ConvertExit，程序退出时这块内存靠进程结束被 OS 回收。严格说应该在退出前调 ConvertExit 释放，或做 signal 处理。

## Q11. initLut 是什么时候调用的？为什么要在那个时机？

**参考答案：**

`initLut()` 在 **`Yuv2RgbInit()` 里调用**，也就是转换器注册时（初始化阶段）就建好查找表：
```c
int Yuv2RgbInit(void){
    initLut();   // 初始化颜色查找表
    return RegisterVideoConvert(&g_tYuv2RgbConvert);
}
```

**为什么在初始化时**：查找表的内容是固定的（256 个系数值），只需算一次。放在初始化阶段（程序启动时）算好，之后每一帧转换都直接查表，**避免每帧重复计算 256 个浮点值**。这是「一次计算，多次使用」的优化。

**追问：g_lutRv 这些数组是静态全局的，多线程安全吗？**
初始化后它们是**只读**的（不再修改），只读数据多线程并发访问是安全的。风险只在于如果多线程同时调用 initLut（重复写）——但本项目只在初始化时调一次，没问题。

## Q12. CovertOneLine 里为什么判断 iSrcBpp != 24 就返回错误？

**参考答案：**

```c
if (iSrcBpp != 24) return -1;
```
因为 libjpeg 解码 JPEG（非灰度、非 CMYK 的常规彩色图）默认输出的是 **RGB888，即每像素 24 位**（`jpeg_read_scanlines` 读出的 aucLineBuffer 就是 24bpp）。`CovertOneLine` 的输入固定是 24bpp，然后转成目标的 16 或 32bpp：
```c
if (iDstBpp == 32) dwColor = (R<<16)|(G<<8)|B;   // 24→32
else if (iDstBpp == 16) { R>>3; G>>2; B>>3; ... } // 24→16(RGB565)
```
这个检查是**防御性编程**：确保输入格式符合预期，不符合就报错，避免按错误的字节数解析数据导致花屏或越界。

**追问：如果想让 libjpeg 直接输出 RGB565 省一步转换，可以吗？**
libjpeg 支持设置 `out_color_space` 和量化，但不直接支持 RGB565 打包，通常还是解出 RGB888 再自己转。有些优化会用 libjpeg-turbo 的 `JCS_RGB565` 扩展直接输出 565，本项目用的是标准流程。

## Q13. 颜色转换过程中，颜色值为什么会溢出？怎么处理的？

**参考答案：**

YUV→RGB 的公式里，比如 `R = Y + 1.4075*(V-128)`：
- Y 最大 255，`1.4075*(V-128)` 当 V=255 时约 +179，加起来可能超过 255。
- 当 V=0 时约 -180，Y 较小时结果可能是**负数**。

RGB 分量合法范围是 0~255，超出会导致数据回绕（比如 256 变成 0）产生错误颜色。

**解决**：用 **CLIP 宏裁剪**：
```c
#define CLIP(color) (unsigned char)(((color)>0xFF)?0xff:(((color)<0)?0:(color)))
```
大于 255 截成 255，小于 0 截成 0。所有 R_FROMYV/G_FROMYUV/B_FROMYU 都用 CLIP 包裹，保证输出在合法范围。这是图像处理里处理颜色溢出的标准做法（饱和处理/saturation）。

## Q14.（陷阱题）转换时如果输入图像宽高和输出缓冲区不匹配会怎样？

**参考答案：**

各转换函数里，输出的宽高是**从输入拷贝**的：
```c
ptPixelDatasOut->iWidth  = ptPixelDatasIn->iWidth;
ptPixelDatasOut->iHeight = ptPixelDatasIn->iHeight;
```
然后按这个宽高计算 iTotalBytes 并 malloc。所以正常情况下输出缓冲区大小和输入匹配。

**但有个隐患**：`if(!aucPixelDatas) malloc(...)` 只在指针为空时分配。如果**分辨率在运行中改变**（比如摄像头动态切换格式），输出宽高变了但缓冲区已经分配过（指针非空），就**不会重新 malloc**，会用旧的小缓冲区写新的大图像，造成**缓冲区溢出**。

本项目因为初始化时就固定了分辨率（S_FMT 后不变），不会触发这个问题。但作为改进，应该在检测到尺寸变化时重新分配缓冲区。这体现了对边界条件的思考。

## 附：颜色格式速查

| 格式 | bpp | 说明 |
|------|-----|------|
| YUYV (YUV422) | 16 | 未压缩，4 字节 2 像素 [Y0 U0 Y1 V0]，UV 共享 |
| MJPEG | - | 压缩，每帧是独立 JPEG，需 libjpeg 解码 |
| RGB888 | 24 | 每像素 R/G/B 各 1 字节（libjpeg 解码输出） |
| RGB565 | 16 | R5 G6 B5，绿色多 1 位（人眼敏感） |
| RGB32 | 32 | 0x00RRGGBB，4 字节对齐，含 padding/alpha |

**转换路径：**
```
YUYV   ──yuv2rgb──>  RGB565 / RGB32
MJPEG  ──libjpeg──> RGB888 ──CovertOneLine──> RGB565 / RGB32
RGB565 ──rgb2rgb──> RGB565(拷贝) / RGB32(扩展)
```

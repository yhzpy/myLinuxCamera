# 02 · V4L2 视频采集模块深度拷打

> V4L2（Video for Linux 2）是本项目最核心、面试官最爱深挖的模块。对应源码：`video/v4l2.c`、`video/video_manager.c`、`include/video_manager.h`。

---

## Q1. 什么是 V4L2？为什么用它？

**参考答案：**

V4L2（Video for Linux 2）是 Linux 内核提供的**视频设备驱动框架/接口标准**，用于统一操作摄像头、视频采集卡、TV 卡等视频设备。它把各种厂商的硬件差异抽象成一套标准的 `ioctl` 命令和数据结构，应用层不用关心底层硬件，用统一的 API 就能采集视频。

用它的原因：Linux 下操作 USB 摄像头（UVC 设备）的标准方式就是 V4L2，设备节点是 `/dev/video0`、`/dev/video1` 等。

---

## Q2. 详细讲讲 V4L2 采集的完整流程（这是必考题）

**参考答案：**

V4L2 采集分**初始化**和**采集循环**两个阶段，核心是一系列 `ioctl` 命令：

### 初始化阶段
1. **`open("/dev/videoX", O_RDWR)`** —— 打开设备，拿到文件描述符 fd。
2. **`VIDIOC_QUERYCAP`** —— 查询设备能力（`struct v4l2_capability`）：是不是视频捕获设备（`V4L2_CAP_VIDEO_CAPTURE`）、支不支持 streaming（`V4L2_CAP_STREAMING`）、支不支持 read/write（`V4L2_CAP_READWRITE`）。
3. **`VIDIOC_ENUM_FMT`** —— 枚举设备支持的像素格式（`struct v4l2_fmtdesc`），用 index 递增遍历，选出我们支持的格式（MJPEG/YUYV/RGB565）。
4. **`VIDIOC_S_FMT`** —— 设置采集格式（`struct v4l2_format`）：分辨率（宽×高）、像素格式、场序（field）。注意驱动可能不支持你设的值，会**修改后回填**，要以返回的结构体为准。
5. **`VIDIOC_REQBUFS`** —— 向驱动申请缓冲区（`struct v4l2_requestbuffers`），本项目申请 `NB_BUFFER=4` 个，类型 `V4L2_MEMORY_MMAP`。
6. **`VIDIOC_QUERYBUF`** —— 查询每个缓冲区的长度和偏移（`struct v4l2_buffer`），然后 **`mmap`** 把它映射到用户空间。
7. **`VIDIOC_QBUF`** —— 把所有缓冲区**入队**，交给驱动去填充数据。

### 采集循环阶段
8. **`VIDIOC_STREAMON`** —— 启动数据流，驱动开始采集。
9. **`poll()`** —— 阻塞等待，直到有缓冲区装满数据（`POLLIN` 就绪）。
10. **`VIDIOC_DQBUF`** —— **出队**一个装满数据的缓冲区，拿到它的 index。
11. **处理数据**（转换/缩放/显示）。
12. **`VIDIOC_QBUF`** —— 把用完的缓冲区**重新入队**，供驱动下次采集。
13. 回到第 9 步循环。
14. 退出时 **`VIDIOC_STREAMOFF`** 停止，`munmap` 解除映射，`close(fd)`。

## Q3. VIDIOC_QUERYCAP 查出来的 capabilities 你怎么用？

**参考答案：**

代码里查了三个标志位：
```c
if(!(tV4l2Cap.capabilities & V4L2_CAP_VIDEO_CAPTURE))  // 不是捕获设备就报错退出
if(tV4l2Cap.capabilities & V4L2_CAP_STREAMING)         // 支持流式 → 走 mmap 分支
if(tV4l2Cap.capabilities & V4L2_CAP_READWRITE)         // 支持读写 → 走 read 分支
```
`capabilities` 是个位掩码，用 `&` 按位与判断某能力是否具备。本项目**优先判断 STREAMING**，支持就用 mmap 高效路径；否则退而用 READWRITE 路径。

## Q4. 为什么设置格式 VIDIOC_S_FMT 之后，要重新读取 tV4l2Fmt 里的宽高？

**参考答案：**

因为**驱动不一定完全支持你请求的参数**。比如你请求 800×480，但摄像头最近的支持分辨率是 640×480，驱动会自动调整成它支持的值，并**回填到同一个结构体**返回给应用。

所以代码里设置完格式后：
```c
iError = ioctl(iFd, VIDIOC_S_FMT, &tV4l2Fmt);
ptVideoDevice->iWidth  = tV4l2Fmt.fmt.pix.width;   // 用驱动实际返回的值
ptVideoDevice->iHeight = tV4l2Fmt.fmt.pix.height;
```
必须以**驱动返回的实际值**为准，否则后续按错误的宽高处理数据会花屏或越界。

## Q5. 讲讲 V4L2 的缓冲区队列机制（QBUF/DQBUF），为什么要这么设计？

**参考答案（重点，体现理解深度）：**

这是一个典型的**生产者-消费者模型**：
- **驱动 = 生产者**：不断从摄像头硬件采集图像数据，写入「已入队（queued）」的空缓冲区。
- **应用 = 消费者**：通过 DQBUF 取出「已装满数据」的缓冲区，处理完再通过 QBUF 还回去。

内核维护两个队列：**输入队列（应用→驱动，空的待填充）** 和 **输出队列（驱动→应用，满的待处理）**。

**为什么要多个缓冲区（4 个）轮转？**
1. **避免竞争/丢帧**：如果只有 1 个缓冲区，驱动采集下一帧时应用还在处理上一帧，会冲突或丢数据。多缓冲区让「采集」和「处理」可以并行流水线化。
2. **提高吞吐**：驱动可以提前把后续帧填到其它空闲缓冲区，应用处理完一个立刻有下一个可用，减少等待。

类比：餐厅准备了 4 个盘子（缓冲区），全部放到传菜口（QBUF 入队），厨师（驱动）做好菜端出（DQBUF），客人吃完（处理）把空盘放回（QBUF），循环使用。

## Q6. mmap 在这里是怎么用的？参数什么含义？

**参考答案：**

```c
ptVideoDevice->pucVideBuf[i] = mmap(0, tV4l2Buf.length, PROT_READ,
                                    MAP_SHARED, iFd, tV4l2Buf.m.offset);
```
- **参数1 = 0**：让内核自行选择映射到用户空间的起始地址。
- **`tV4l2Buf.length`**：映射长度，即该缓冲区大小（QUERYBUF 返回）。
- **`PROT_READ`**：映射区域只读（数据由内核写入，用户只读）。
- **`MAP_SHARED`**：共享映射，用户空间和内核看到**同一块物理内存**，这是零拷贝的关键。
- **`iFd`**：设备文件描述符。
- **`tV4l2Buf.m.offset`**：该缓冲区在设备内存中的偏移（每个缓冲区偏移不同，QUERYBUF 返回）。

映射成功后，`pucVideBuf[i]` 这个用户态指针就直接指向内核的采集缓冲区，DQBUF 后直接读它即可，**无需拷贝数据**。

**追问：为什么用 PROT_READ 而不是 PROT_READ|PROT_WRITE？**
因为摄像头采集是内核往缓冲区写、应用只读取，用户空间不需要写权限，只读更安全。（而 framebuffer 那边需要写显存，用的是 `PROT_READ|PROT_WRITE`。）

## Q7. streaming 模式和 read/write 模式的区别？你代码里怎么处理的？

**参考答案：**

| | Streaming（mmap） | Read/Write |
|---|---|---|
| 数据获取 | mmap 内核缓冲区，DQBUF/QBUF 轮转，零拷贝 | `read(fd, buf, size)` 每帧拷贝到用户缓冲区 |
| 缓冲区 | 内核分配多个（本项目 4 个） | 用户自己 malloc（本项目 1 个） |
| 性能 | 高 | 低（有拷贝开销） |
| 复杂度 | 高（要管理队列） | 简单 |

代码里根据 `capabilities` 分支处理：
- **Streaming**：QUERYBUF + mmap 映射 4 个缓冲区，全部 QBUF 入队；GetFrame 用 `V4l2GetFrameForStreaming`（poll + DQBUF）。
- **ReadWrite**：malloc 1 个用户缓冲区，大小按 `宽×高×4` 保守估计；**动态修改函数指针** `g_tV4l2VideoOpr.GetFrame = V4l2GetFrameForReadWrite`，让取帧走 `read()`。

这个「运行时替换函数指针」是个技巧：让上层 `GetFrame()` 调用无感知地切换到不同实现，体现了函数指针多态的灵活。

## Q8. poll() 在这里的作用？为什么不用 read 直接阻塞？超时设成 -1 是什么意思？

**参考答案：**

`poll()` 是 **I/O 多路复用**机制，用来**等待设备文件描述符就绪**（有数据可读）：
```c
tFds[0].fd = ptVideoDevice->iFd;
tFds[0].events = POLLIN;   // 关心「可读」事件
iRet = poll(tFds, 1, -1);  // -1 表示无限阻塞，直到有数据
```
- **为什么用 poll**：streaming 模式下数据不是通过 read 读的，而是内核填到 mmap 缓冲区，需要一个机制「等到有缓冲区就绪」再去 DQBUF。poll 正好能监听 fd 的 POLLIN 事件（表示有帧采集完成）。
- **超时 -1**：无限期阻塞，直到有数据到来才返回。如果设成正数（如 2000ms），超时返回 0，可用于防止摄像头卡死时程序永久挂起。
- **相比 select**：poll 没有 fd 数量限制（select 有 FD_SETSIZE 1024 限制），接口更清晰。

**追问：poll 返回值怎么判断？**
`iRet <= 0` 表示出错（<0）或超时（=0），代码里当作错误处理返回 -1；`>0` 表示有 fd 就绪，继续 DQBUF。

## Q9. DQBUF 之后你怎么知道这一帧的数据在哪、有多大、什么格式？

**参考答案：**

DQBUF 返回的 `struct v4l2_buffer tV4l2Buf` 里带了关键信息：
- **`tV4l2Buf.index`**：这是第几个缓冲区，用它去 `pucVideBuf[index]` 找到 mmap 的数据地址。
- **`tV4l2Buf.bytesused`**：这一帧实际用了多少字节（对 MJPEG 这种变长压缩格式尤其重要，实际数据量小于缓冲区容量）。

然后填充应用层的 `T_VideoBuf`：
```c
ptVideoBuf->iPixelFormat = ptVideoDevice->iPixelFormat;         // 格式（初始化时定的）
ptVideoBuf->tPixelDatas.iWidth/iHeight = ...;                   // 宽高
ptVideoBuf->tPixelDatas.iBpp = YUYV?16 : MJPEG?24 : RGB565?16;  // 按格式设 bpp
ptVideoBuf->tPixelDatas.iTotalBytes = tV4l2Buf.bytesused;       // 实际字节数
ptVideoBuf->tPixelDatas.aucPixelDatas = pucVideBuf[index];      // 数据地址（指向 mmap 内存）
```
注意 `aucPixelDatas` 直接指向 mmap 的内核缓冲区，**没有拷贝**，这是零拷贝的体现。

## Q10. PutFrame 归还缓冲区时，index 从哪来？

**参考答案：**

DQBUF 时代码把 index 存到了设备结构体：`ptVideoDevice->iVideoBufCurIndex = tV4l2Buf.index;`。
PutFrame（`V4l2PutFrameForStreaming`）再用这个 index 构造 `v4l2_buffer` 调 QBUF 归还：
```c
tV4l2Buf.index = ptVideoDevice->iVideoBufCurIndex;
ioctl(fd, VIDIOC_QBUF, &tV4l2Buf);
```

**⚠️ 这里有个可讨论的设计问题（面试官可能挖坑）**：用单个 `iVideoBufCurIndex` 变量记录当前帧 index，隐含假设「取一帧、处理一帧、还一帧」严格串行。如果将来改成流水线并行（同时持有多帧），这个单变量就不够用了，应该让 index 跟着 `T_VideoBuf` 走（每个 buf 记住自己的 index）。这是可扩展性上的一个改进点。

## Q11. T_VideoDevice 和 T_VideoBuf 这两个结构体分别是干什么的？为什么要分开？

**参考答案：**

- **`T_VideoDevice`（设备）**：描述**一个摄像头设备的整体状态**——fd、像素格式、宽高、缓冲区数量、mmap 地址数组 `pucVideBuf[NB_BUFFER]`、当前 index、操作接口指针 `ptOPr`。生命周期 = 整个程序运行期。
- **`T_VideoBuf`（帧数据）**：描述**单独一帧图像**——像素数据 `T_PixelDatas` + 格式。生命周期 = 一帧的处理过程。

**为什么分开**：一个设备会源源不断产生很多帧，设备信息是「不变的上下文」，帧数据是「流动的数据」。分开后，`T_VideoBuf` 可以作为**统一的图像载体**在采集、转换、缩放、显示各模块间传递，模块之间不需要知道设备细节，降低了耦合。

**关键点**：DQBUF 得到的 `T_VideoBuf.aucPixelDatas` 和设备的 `pucVideBuf[index]` 是**同一块 mmap 内存**，只是换了个抽象视角（应用层用 T_VideoBuf，内核层是 mmap 缓冲区）。

## Q12. 你支持哪几种像素格式？枚举格式时是怎么选的？

**参考答案：**

支持三种（`g_aiSupportedFormats`）：
```c
static int g_aiSupportedFormats[] = {V4L2_PIX_FMT_MJPEG, V4L2_PIX_FMT_YUYV, V4L2_PIX_FMT_RGB565};
```

枚举时用 `VIDIOC_ENUM_FMT`，index 从 0 递增，内核每次返回一个设备支持的格式，用 `isSupportThisFormat()` 检查是否在我们的支持列表里，**第一个匹配的就选中并 break**：
```c
tFmtDesc.index = 0;
while(ioctl(iFd, VIDIOC_ENUM_FMT, &tFmtDesc) == 0){
    if(isSupportThisFormat(tFmtDesc.pixelformat)){
        ptVideoDevice->iPixelFormat = tFmtDesc.pixelformat;
        break;
    }
    tFmtDesc.index++;
}
```

**⚠️ 注意点**：数组里 MJPEG 排第一，意味着如果设备同时支持 MJPEG 和 YUYV，会**优先选 MJPEG**。MJPEG 是压缩格式，同样 USB 2.0 带宽下能传更高分辨率/帧率，但需要解码（CPU 开销）。这里的优先级是个可讨论的权衡点。

**追问：如果枚举完一个都不支持怎么办？**
`ptVideoDevice->iPixelFormat` 保持 0（因为 VideoDeviceInit 里 memset 过设备结构体），代码检测到 `iPixelFormat == 0` 就报错 `goto err_exit`。

## Q13. YUYV 和 MJPEG 格式有什么区别？各有什么优劣？

**参考答案：**

- **YUYV（YUV422 packed）**：**未压缩**的原始像素格式。每 4 字节表示 2 个像素：`[Y0 U0 Y1 V0]`，两个像素共享一组 UV（色度），各自有 Y（亮度）。优点是无需解码、CPU 占用低、延迟小；缺点是**数据量大**（16bpp），高分辨率下受 USB 带宽限制，帧率上不去。

- **MJPEG**：每一帧都是一张独立的 **JPEG 压缩图**。优点是压缩比高、数据量小，同带宽下能支持更高分辨率/帧率；缺点是**需要 CPU 解码**（本项目用 libjpeg），有解码开销和一定延迟。

选择依据：如果 CPU 强、要低延迟用 YUYV；如果带宽紧张、要高分辨率用 MJPEG。

## Q14. VIDIOC_REQBUFS 申请 4 个缓冲区，内核一定给你 4 个吗？

**参考答案：**

不一定。`REQBUFS` 传入的 `count` 是**请求值**，内核会根据内存等情况调整，并把**实际分配的数量回填到 `count`**。所以代码里以返回值为准：
```c
tV4l2ReqBuffs.count = NB_BUFFER;   // 请求 4 个
ioctl(iFd, VIDIOC_REQBUFS, &tV4l2ReqBuffs);
ptVideoDevice->iVideoBufCnt = tV4l2ReqBuffs.count;  // 用实际分配的数量
```
后续循环都用 `iVideoBufCnt` 而不是硬编码的 4，这是健壮性写法。

## Q15. 设备关闭 / 资源释放你是怎么做的？

**参考答案：**

`V4l2ExitDevice()` 里：
```c
for (i = 0; i < iVideoBufCnt; i++)
    if (pucVideBuf[i]) { munmap(pucVideBuf[i], iVideoBufMaxLen); pucVideBuf[i] = NULL; }
close(ptVideoDevice->iFd);
```
逐个 `munmap` 解除内存映射，再 `close(fd)`。

初始化失败时用 **`goto err_exit`** 统一清理：所有失败分支跳到 `err_exit:` 标签，先 `close(iFd)` 再 `return -1`，保证文件描述符不泄漏。这是 Linux C 编程的经典错误处理模式（内核代码里也大量使用）。

**⚠️ 可改进点**：`err_exit` 目前只 close 了 fd，如果失败发生在 mmap 之后（比如某个缓冲区映射失败），前面已映射成功的缓冲区没有 munmap，理论上有内存泄漏。更严谨的做法是 err_exit 里也遍历 munmap 已映射的缓冲区。另外主程序 while(1) 是死循环，实际没调用 StopDevice/ExitDevice，退出靠 Ctrl+C，也没做 signal 处理优雅释放。

## Q16. video_manager.c 里的注册机制是怎么工作的？

**参考答案：**

`video_manager.c` 维护一个**函数指针结构体链表**，头指针 `ptVideoOprHeader`：

- **`RegisterVideoOpr()`**：尾插法把新的 `T_VideoOpr` 加入链表。
- **`getVideoOpr(name)`**：遍历链表，`strcmp` 匹配名字，返回对应结构体。
- **`VideoInit()`**：调用 `V4l2Init()`，后者把 `g_tV4l2VideoOpr`（填好了 name 和各函数指针）注册进链表。
- **`VideoDeviceInit(devName, device)`**：`getVideoOpr("v4l2")` 拿到接口，绑定到 `device->ptOPr`，再调 `ptOPr->InitDevice()`。

这套「注册-查找-调用」机制让 main.c 只跟管理器打交道，不直接依赖 v4l2.c，实现解耦。加新驱动只需注册新的结构体。

## Q17. GetFrame 失败时 main 里是 continue，为什么不是直接退出？

**参考答案：**

这体现了**错误分类处理**的思想：
- **初始化阶段的错误**（打开设备失败、设置格式失败）是**致命错误**，直接 `return -1` 退出，因为没有设备就没法继续。
- **采集循环中的单帧错误**（某一帧 DQBUF 失败）是**可恢复错误**，`continue` 跳过这一帧，尝试采集下一帧，避免偶发的单帧错误（如瞬时 I/O 抖动）导致整个程序崩溃。

视频流是实时的，丢一帧无所谓，重要的是保持循环不中断。这是实时系统里常见的容错策略。

## Q18.（陷阱题）你的 main 函数签名 `int main(int argc, char *argv)` 有问题吗？

**参考答案（诚实 + 展示功底）：**

有问题。标准签名应该是 `int main(int argc, char *argv[])` 或 `char **argv`。这里写成了 `char *argv`（单个字符指针）。

- `argv` 类型是 `char *`，那么 `argv[1]` 实际是 `*(argv + 1)`，取的是**指针所指向字符串的第 2 个字符**（一个 char），而不是第二个命令行参数（char*）。
- 传给 `VideoDeviceInit(argv[1], ...)`（形参是 `char *`）时类型不匹配，正常编译器会报警告甚至错误。

这是复盘时发现的一个 bug，正确写法是 `char *argv[]`。**面试中主动指出自己代码的问题，比藏着掖着更能体现工程素养。**（注：如果实际能跑通，可能是特定环境/编译器行为，但语义上确实不规范，应修正。）

# 01 · 项目概览与自我介绍

> 面试开场：如何在 2~5 分钟内把这个项目讲清楚、讲出彩。

---

## Q1. 请用一两分钟介绍一下你这个项目

**参考答案：**

这是一个运行在嵌入式 Linux（imx6ull，ARM Cortex-A7）上的**实时相机显示系统**，功能是：把 USB 摄像头拍到的画面，实时显示到板子的 LCD 屏幕上。

整体是一条**图像流水线**：

```
摄像头采集 → 格式转换 → 缩放 → 居中合并 → 刷屏显示 → 归还缓冲区 → 循环
 (V4L2)      (YUV/MJPEG   (最近邻    (PicMerge)  (framebuffer)  (QBUF)
              →RGB)        插值)
```

分成 4 个功能模块 + 1 个主程序：
- **video/**：基于 V4L2 采集摄像头数据，封装了 streaming（mmap）和 read/write 两种取帧方式。
- **convert/**：格式转换，支持 YUV422→RGB、MJPEG→RGB、RGB565→RGB32，用管理框架自动选择转换器。
- **display/**：基于 Framebuffer 直接操作 LCD 显存，支持 8/16/32 位色深。
- **render/**：图像缩放（最近邻插值）和合并（居中显示）。
- **main.c**：协调以上模块，跑主循环。

技术亮点是：**用 C 语言面向对象的思路做模块解耦**——每个模块通过「函数指针结构体 + 链表注册」实现插件式扩展；采集用 **mmap 零拷贝 + 多缓冲区轮转**；YUV 转换用**查找表**优化性能。

## Q2. 这个项目的整体架构是怎样的？画个图 / 讲讲分层

**参考答案：**

采用**分层模块化架构**，依赖方向严格自上而下，上层通过函数指针调用下层，下层不感知上层：

```
                    ┌──────────────────────────┐
                    │         main.c           │  应用层：编排流水线
                    │  (初始化 + 主循环)         │
                    └──────────────────────────┘
                       │        │        │        │
          ┌────────────┘        │        │        └────────────┐
          ▼                     ▼        ▼                     ▼
  ┌───────────────┐   ┌──────────────┐ ┌──────────────┐ ┌────────────┐
  │ disp_manager  │   │video_manager │ │convert_manager│ │   render   │  管理层
  └───────────────┘   └──────────────┘ └──────────────┘ └────────────┘
          │                     │              │                │
          ▼                     ▼              ▼                ▼
  ┌───────────────┐   ┌──────────────┐ ┌──────────────┐ ┌────────────┐
  │     fb.c      │   │    v4l2.c    │ │ yuv2rgb.c    │ │  zoom.c    │  驱动/算法层
  │ (Framebuffer) │   │  (V4L2 驱动) │ │ mjpeg2rgb.c  │ │  merge.c   │
  │               │   │              │ │ rgb2rgb.c    │ │            │
  └───────────────┘   └──────────────┘ └──────────────┘ └────────────┘
```

**核心抽象**：三个「操作接口结构体」是解耦的关键——
- `T_VideoOpr`：抽象视频设备（InitDevice/GetFrame/PutFrame/StartDevice...）
- `T_DispOpr`：抽象显示设备（DeviceInit/ShowPixel/CleanScreen/ShowPage）
- `T_VideoConvert`：抽象转换器（isSupport/Convert/ConvertExit）

每个具体驱动（如 v4l2、fb、yuv2rgb）实现这些函数指针并**注册到链表**，管理器根据名字或格式**查找匹配的实现**。这样加一个新摄像头驱动或新格式转换器，只需要实现接口 + 注册，不用改主流程。

**统一数据载体**：所有图像数据都用 `T_PixelDatas`（宽、高、bpp、行字节、总字节、数据指针）表示，在各模块间传递，避免了模块间的数据格式耦合。

## Q3. 讲讲你这个项目的主流程 / 数据是怎么流动的

**参考答案：**

**初始化阶段**（main.c 顺序执行）：
1. `DisplayInit()` → 注册 fb 显示驱动到链表
2. `SelectAndInitDefaultDispDev("fb")` → 打开 /dev/fb0，ioctl 获取屏幕参数，mmap 映射显存，清屏
3. `GetDispResolution()` → 拿到 LCD 的宽、高、bpp
4. `GetVideoBufForDisplay()` → 构造一个直接指向 framebuffer 显存的 `tFrameBuf`
5. `VideoInit()` → 注册 v4l2 驱动
6. `VideoDeviceInit(argv[1])` → 打开摄像头，QUERYCAP/ENUM_FMT/S_FMT/REQBUFS/QUERYBUF/mmap/QBUF
7. `VideoConvertInit()` → 注册 yuv2rgb/mjpeg2rgb/rgb2rgb 三个转换器
8. `GetVideoConvertForFormats()` → 根据「摄像头格式 → LCD 格式」找到匹配的转换器
9. `StartDevice()` → VIDIOC_STREAMON 开始采集

**主循环阶段**（while(1)）：
```
GetFrame()   从摄像头出队一帧（poll 等待 + DQBUF）
   ↓
Convert()    如果摄像头格式 != LCD 格式，转成 RGB（结果放 tConvertBuf）
   ↓
PicZoom()    如果图像比 LCD 大，等比缩放（结果放 tZoomBuf）
   ↓
PicMerge()   计算居中坐标，把图像合并到 tFrameBuf（framebuffer 显存）
   ↓
FlushPixelDatasToDev()  ShowPage 把数据刷到 LCD
   ↓
PutFrame()   把缓冲区 QBUF 归还给驱动，采集下一帧
```

**一个关键设计**：用一个 `ptVideoBufCur` 指针做「当前待处理图像」的游标。每经过一步处理（转换/缩放），就把游标指向新的缓冲区，最后统一 Merge 到 framebuffer。这样避免了大量 if-else 分支判断，代码很清晰。

## Q5. 你在项目里负责了什么？（假设是全独立完成）

**参考答案（可按实际情况调整）：**

我从 0 到 1 完成了整个项目：
1. **搭建分层架构**：设计了 video/display/convert/render 四个模块的管理器 + 驱动接口，用函数指针结构体做抽象。

## Q6. 这个项目最大的难点 / 你觉得最有挑战的地方是什么？

**参考答案（挑 1~2 个深入讲，详见 07 文档）：**

**难点一：V4L2 的缓冲区队列机制（QBUF/DQBUF）**
刚开始不理解为什么要「入队—出队—再入队」这么绕。后来明白：这是**生产者-消费者模型**——驱动（生产者）往已入队的空缓冲区里写数据，应用（消费者）通过 DQBUF 取出装满数据的缓冲区，处理完再 QBUF 还回去。多个缓冲区轮转，避免了「一边采集一边处理」的数据竞争和丢帧。

**难点二：交叉编译时 libjpeg 依赖**
MJPEG 解码需要 libjpeg，但直接在虚拟机 `apt install libjpeg-dev` 装的是 x86 版本，ARM 板子用不了。最后通过交叉编译 libjpeg-turbo 源码 / 拷贝板子 rootfs 里的 ARM 版 .so 到工具链 sysroot 解决。

**难点三：颜色格式转换的正确性与性能**
YUV→RGB 涉及浮点运算，逐像素算太慢。用查找表把 `1.4075*(V-128)` 这类系数预先算好存表，运行时查表 + 整数加法，性能提升明显。同时要注意颜色值裁剪（CLIP 到 0~255）防止溢出。

## Q7. 项目有什么可以改进 / 你觉得哪里做得不够好？

**参考答案（体现批判性思维，非常重要，面试官爱问）：**

诚实地讲，有几个地方可以优化：

1. **单线程同步阻塞**：目前采集、转换、显示都在一个线程串行执行，如果某一步慢会拖累帧率。可以拆成**采集线程 + 处理线程 + 显示线程**，用环形缓冲队列解耦，提高吞吐。

2. **没有双缓冲，可能画面撕裂**：现在直接往 framebuffer 显存写，写的过程中 LCD 正在扫描输出，理论上可能出现撕裂（tearing）。代码里其实预留了 `VideoMem` 多缓冲机制（`AllocVideoMem/GetVideoMem`），但主流程没启用，可以配合双缓冲 + 垂直同步解决。

3. **缩放算法较简单**：最近邻插值速度快但有锯齿，可以升级为双线性插值提升画质（牺牲一点性能）。

4. **只缩小不放大**：当前只在图像大于 LCD 时缩放，小图不放大，可以补充。

5. **错误处理较朴素**：目前是整型返回码 + `DBG_PRINTF` + goto 清理，没有统一错误码枚举，生产环境可以加强。

6. **代码里有个隐患**：`main` 函数签名写成了 `int main(int argc, char *argv)`（少了 `[]`），严格说 `argv` 应该是 `char *argv[]`。虽然某些编译器能过，但 `argv[1]` 的语义是有问题的，这是我复盘时发现的、需要修正的点。

> 💡 面试技巧：主动说出不足 + 给出改进方案，比假装完美更能赢得面试官好感。

## Q8. 为什么用 mmap 而不是直接 read 读摄像头数据？

**参考答案：**

`read()` 方式每读一帧都要把数据从**内核缓冲区拷贝到用户缓冲区**，对于视频流这种大数据量、高频率的场景，拷贝开销很大。

`mmap` 方式把内核的缓冲区**直接映射到用户空间地址**，用户态指针和内核态指向同一块物理内存，取帧时**零拷贝**（只需 DQBUF 改变缓冲区状态，不用搬数据），性能高很多。所以本项目优先用 streaming + mmap，read/write 只作为兼容性备选。

## Q9. 如果让你支持一个新的摄像头（比如网络摄像头 IP Camera）或新的显示设备（比如 HDMI），怎么改？

**参考答案（考察对架构可扩展性的理解）：**

这正是我这套架构的优势所在，**几乎不用改主流程**：

- **加新视频设备**：新建一个 `ipcam.c`，实现 `T_VideoOpr` 里的 InitDevice/GetFrame/PutFrame 等函数指针，构造一个 `g_tIpCamOpr` 结构体，写个 `IpCamInit()` 调用 `RegisterVideoOpr()` 注册进链表。然后 `VideoDeviceInit` 里根据设备名选择即可。
- **加新显示设备**：同理，新建 `hdmi.c` 实现 `T_DispOpr`（DeviceInit/ShowPixel/CleanScreen/ShowPage），注册进显示链表，`SelectAndInitDefaultDispDev("hdmi")` 就能切换。
- **加新格式转换器**：实现 `T_VideoConvert`（isSupport/Convert），注册后 `GetVideoConvertForFormats` 会自动匹配。

这就是**插件式架构 / 依赖倒置**：上层依赖抽象接口，不依赖具体实现，符合开闭原则（对扩展开放，对修改关闭）。

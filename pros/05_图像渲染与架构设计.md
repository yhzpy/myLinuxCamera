# 第一部分：图像渲染算法

## Q1. 讲讲最近邻插值缩放算法的原理

**参考答案（对应 zoom.c 的 PicZoom）：**

**最近邻插值（Nearest Neighbor Interpolation）**：缩放时，目标图像的每个像素，取源图像中**位置最接近的那个像素**的值，直接搬过来，不做任何插值计算。

**坐标映射**：目标像素 (x, y) 对应源像素坐标：
```
srcX = x * srcWidth / dstWidth
srcY = y * srcHeight / dstHeight
```
用**整数除法**（自动向下取整），找到对应的源像素。

代码实现：
```c
// 预先算好每一列的源 X 坐标映射表（避免内层循环重复计算）
for (x = 0; x < dwDstWidth; x++)
    pdwSrcXTable[x] = x * ptOriginPic->iWidth / ptZoomPic->iWidth;

// 逐行处理
for (y = 0; y < ptZoomPic->iHeight; y++){
    dwSrcY = y * ptOriginPic->iHeight / ptZoomPic->iHeight;   // 目标行 → 源行
    pucDest = 目标 + y * 目标行字节;
    pucSrc  = 源 + dwSrcY * 源行字节;
    for (x = 0; x < dwDstWidth; x++)
        // 从源 (pdwSrcXTable[x], dwSrcY) 拷贝一个像素到目标 (x, y)
        memcpy(pucDest + x*像素字节, pucSrc + pdwSrcXTable[x]*像素字节, 像素字节);
}
```

**优点**：算法简单、计算量小、速度快（只是取像素，无浮点、无加权）。
**缺点**：缩放后图像有**锯齿（马赛克感）**，尤其是放大时明显，因为丢弃了中间像素信息。

## Q2. PicZoom 里为什么要建一个 X 坐标查找表 pdwSrcXTable？

**参考答案（性能优化细节）：**

```c
pdwSrcXTable = malloc(sizeof(unsigned long) * dwDstWidth);
for (x = 0; x < dwDstWidth; x++)
    pdwSrcXTable[x] = x * ptOriginPic->iWidth / ptZoomPic->iWidth;
```

因为**每一行的 X 坐标映射关系都是相同的**（源列 → 目标列的映射不随 y 变化）。如果不用查找表，内层双重循环里每个像素都要算一次 `x * srcWidth / dstWidth`（含乘法 + 除法，除法尤其慢）。

**优化**：在外层**预先算好一整行的 X 映射**存进表，内层循环直接查表 `pdwSrcXTable[x]`，把「每像素一次乘除」降为「每列一次乘除」，减少了 dstHeight 倍的除法运算。这是典型的**循环外提（loop-invariant code motion）/ 查表优化**。

注意 Y 坐标的映射 `dwSrcY` 放在行循环里算（每行一次），因为它随 y 变化，但一行内不变，所以也是每行算一次而非每像素算。

## Q3. 缩放时为什么要检查 iBpp 一致？缩放和格式转换的先后顺序能调换吗？

**参考答案：**

```c
if (ptOriginPic->iBpp != ptZoomPic->iBpp) return -1;
```
PicZoom 是按**字节拷贝**像素的（memcpy 像素字节），它不关心像素是什么格式，只要求源和目标每像素字节数一致，否则拷贝的字节数对不上会错位。

**顺序问题**：本项目主流程是**先转换格式，再缩放**：
```
Convert (YUV→RGB, bpp 变成 LCD 的 bpp) → PicZoom (在 RGB 域缩放)
```
这个顺序是合理的：
1. 缩放前先把格式统一成 LCD 的 RGB 格式，缩放时源和目标 bpp 就一致了（都是 LCD bpp）。
2. 如果在 YUV 域缩放，YUV422 的「两像素共享 UV」结构会让缩放逻辑复杂化（不能简单按像素搬）。

**理论上更优的顺序**：其实**先缩放再转换**能减少转换的像素量（缩放后像素少了，转换计算量小）。但那样要在 YUV 域缩放，实现复杂。本项目选择了实现简单的「先转换后缩放」，是清晰度/性能的权衡。

## Q4. PicMerge 是怎么把图像居中显示的？

**参考答案（对应 merge.c 和 main.c）：**

**居中坐标计算**（main.c）：
```c
iTopLeftX = (iLcdWidth  - ptVideoBufCur->tPixelDatas.iWidth)  / 2;
iTopLeftY = (iLcdHeight - ptVideoBufCur->tPixelDatas.iHeight) / 2;
```
LCD 尺寸减去图像尺寸，除以 2，就是让图像四周留白相等的左上角坐标。

**合并（merge.c）**：
```c
pucDst = 大图 + iY * 大图行字节 + iX * 大图每像素字节;   // 定位到大图的 (iX,iY)
for (i = 0; i < 小图高度; i++){
    memcpy(pucDst, pucSrc, 小图行字节);   // 逐行拷贝小图到大图
    pucSrc += 小图行字节;
    pucDst += 大图行字节;                  // 注意：大图前进的是大图行字节！
}
```

**关键点**：逐行 memcpy，但源和目标各自的「行步进」不同——源按小图行字节前进，目标按**大图行字节**前进（因为大图一行更长，小图只占中间一段）。这样才能把小图正确"贴"到大图的中间位置，而不是错位。

前置检查：小图不能比大图大，且 bpp 要一致，否则返回 -1。

## Q5. 缩放尺寸是怎么保持宽高比（等比例）计算的？

**参考答案（对应 main.c 的缩放尺寸计算）：**

```c
k = (float)图像高 / 图像宽;              // 原始宽高比
tZoomBuf.宽 = iLcdWidth;                 // 先以 LCD 宽为基准
tZoomBuf.高 = iLcdWidth * k;             // 按比例算高
if (tZoomBuf.高 > iLcdHeight){           // 如果算出的高超出了 LCD 高
    tZoomBuf.宽 = iLcdHeight / k;        // 反过来以高为基准算宽
    tZoomBuf.高 = iLcdHeight;
}
```

逻辑：**先按宽度缩放**，如果缩放后高度还在 LCD 范围内就用它；如果高度超了，说明这个图像比较"高瘦"，就**改按高度缩放**，宽度按比例算。这样保证缩放后的图像**完整落在 LCD 内且不变形**（保持原始宽高比）。

即：以「宽、高哪个先触到边界」为准，等比例缩放到刚好放下。

**⚠️ 注意点**：`k` 用了 float，`iLcdWidth * k` 和 `iLcdHeight / k` 是浮点运算赋值给 int，会截断取整，可能有 1 像素误差，但不影响显示。另外代码只在图像**大于** LCD 时缩放（缩小），小于时不放大，直接居中显示原图。

## Q6.（陷阱题）缩放缓冲区 tZoomBuf 的内存什么时候分配？会不会每帧都 malloc？

**参考答案：**

```c
if (!tZoomBuf.tPixelDatas.aucPixelDatas){
    tZoomBuf.tPixelDatas.aucPixelDatas = malloc(tZoomBuf.tPixelDatas.iTotalBytes);
}
```
和转换器一样的技巧：`tZoomBuf` 在循环外 `memset` 成 0（指针为 NULL），**第一帧进入缩放时 malloc，后续帧因为指针非空跳过 malloc，复用同一块内存**。不会每帧 malloc。

**但有个隐患**：如果缩放后的尺寸会变（比如输入分辨率变化导致 tZoomBuf 宽高变化），iTotalBytes 变了但缓冲区已分配（指针非空），就不会重新 malloc，可能溢出。本项目分辨率固定，不触发。

**另一个点**：只有当「图像大于 LCD」需要缩放时才进这个分支、才分配 tZoomBuf。如果图像一直不大于 LCD，tZoomBuf 永远不分配，ptVideoBufCur 直接指向 tConvertBuf，也没问题。

# 第二部分：架构设计与设计模式

## Q7. 你这个项目用了哪些设计模式？（高频必考）

**参考答案：**

虽然是 C 语言，但项目体现了多种面向对象设计模式：

1. **策略模式（Strategy）**：`T_VideoConvert` 转换器接口，每种转换器是一种"转换策略"，运行时根据格式选择。`T_VideoOpr`、`T_DispOpr` 也是——不同驱动是不同策略。

2. **工厂模式 / 注册表模式（Factory / Registry）**：各 `*_manager` 通过 `Register*` 把实现注册到链表，`Get*(name/format)` 根据条件"生产"出合适的接口实例。相当于一个简单工厂。

3. **责任链模式（Chain of Responsibility）**：`GetVideoConvertForFormats` 遍历链表，逐个问转换器"你支持吗"，直到找到能处理的，这是责任链的变体。

4. **门面/代理模式（Facade）**：管理器层（video_manager/disp_manager/convert_manager）对 main 提供简洁统一的接口，屏蔽底层驱动细节。

5. **单例模式（Singleton）**：全局链表头（g_ptDispOprHead 等）和默认设备（g_ptDefaultDispOpr）是全局唯一的管理实例。

**核心手法**：用**函数指针结构体**模拟"接口/虚函数表"，用**链表 + 注册**模拟"多态和插件管理"。

---

## Q8. C 语言怎么实现"面向对象"？你项目里是怎么做的？

**参考答案（重点，体现 C 语言功底）：**

C 语言没有 class，但可以用**结构体 + 函数指针**模拟面向对象的三大特性：

### 1. 封装（Encapsulation）
把数据和操作数据的函数指针封装在一个结构体里：
```c
struct VideoOpr{
    char *name;                              // 数据
    int (*InitDevice)(...);                  // "方法"
    int (*GetFrame)(...);
    int (*PutFrame)(...);
    ...
};
```
`T_VideoDevice` 里的 `ptOPr` 指向这个"接口"，对象通过它调用方法，类似 `obj->method()`。

### 2. 多态（Polymorphism）
同一个接口 `T_VideoOpr`，不同驱动（v4l2、未来的 ipcam）填不同的函数实现。上层调 `device->ptOPr->GetFrame()` 时，**运行时根据实际绑定的函数指针决定行为**，这就是多态。等价于 C++ 的虚函数表（vtable）——函数指针结构体就是手写的 vtable。

### 3. 继承/接口实现
具体驱动"实现"抽象接口：v4l2.c 填充 `g_tV4l2VideoOpr` 这个结构体的所有函数指针，相当于"实现了 VideoOpr 接口"。

### 静态成员
`static` 全局变量（如 `g_ptVideoOprHead` 链表头）相当于类的静态成员，被所有实例共享。

**一句话总结**：**结构体 = 类，函数指针 = 虚方法，static 全局 = 静态成员，注册链表 = 对象管理**。这是 Linux 内核里也广泛使用的 C 面向对象范式（如 file_operations、各种 ops 结构体）。

## Q9. 为什么用链表管理注册的驱动/转换器，而不是数组？

**参考答案：**

用**单链表（尾插法）**管理：
```c
int RegisterVideoOpr(PT_VideoOpr ptVideoOpr){
    if(ptVideoOprHeader == NULL) ptVideoOprHeader = ptVideoOpr;   // 空链表，作为头
    else{
        PTtmp = ptVideoOprHeader;
        while(PTtmp->ptNext != NULL) PTtmp = PTtmp->ptNext;       // 找到尾
        PTtmp->ptNext = ptVideoOpr;                               // 尾插
        ptVideoOpr->ptNext = NULL;
    }
}
```

**为什么链表**：
1. **动态扩展**：驱动/转换器数量不固定，链表可以运行时任意增删，不用预设大小。
2. **注册解耦**：每个驱动模块在自己的 `Init` 里注册，管理器不需要预先知道有哪些驱动，加新驱动不用改管理器代码（开闭原则）。
3. **结构体内置 ptNext**：`T_VideoOpr` 里有 `ptNext` 指针，结构体自己就是链表节点，不用额外分配节点内存。

**代价**：查找是 O(n) 遍历，但驱动数量很少（个位数），遍历开销可忽略。如果是海量数据才需要考虑数组/哈希表。

## Q10. main.c 里那个 ptVideoBufCur 游标指针的设计好在哪？

**参考答案（代码设计亮点）：**

```c
ptVideoBufCur = &tVideoBuf;              // 初始指向原始帧
if(需要转换){ Convert(&tVideoBuf, &tConvertBuf); ptVideoBufCur = &tConvertBuf; }
if(需要缩放){ PicZoom(ptVideoBufCur, &tZoomBuf); ptVideoBufCur = &tZoomBuf; }
PicMerge(..., ptVideoBufCur, &tFrameBuf);   // 最终合并游标指向的图像
```

**好处**：用一个"当前图像"游标指针，每一步处理后把游标指向新结果。这样：
1. **避免嵌套 if-else**：不用为"转换+缩放""只转换""只缩放""都不做"写四种分支。
2. **流水线清晰**：数据像流水线一样，游标始终指向"最新处理结果"，最后统一 Merge。
3. **易扩展**：想加一步处理（如滤镜），只需在中间插入一步并更新游标，不影响其它逻辑。

这是一种**链式/流水线处理**的优雅写法，值得在面试中主动讲。

## Q11. 三个缓冲区 tVideoBuf / tConvertBuf / tZoomBuf 各自的角色？为什么要分开？

**参考答案：**

| 缓冲区 | 角色 | 数据来源 |
|--------|------|---------|
| `tVideoBuf` | 原始帧 | GetFrame 从摄像头 mmap 缓冲区取（aucPixelDatas 指向内核内存） |
| `tConvertBuf` | 转换后 | Convert 输出，malloc 的用户内存，格式=LCD格式 |
| `tZoomBuf` | 缩放后 | PicZoom 输出，malloc 的用户内存，尺寸=缩放后 |
| `tFrameBuf` | 最终显示 | aucPixelDatas 直接指向 framebuffer 显存 |

**为什么分开**：
1. **数据不能原地覆盖**：tVideoBuf 指向的是摄像头 mmap 缓冲区，处理后要 QBUF 还给驱动，不能在上面乱改；转换/缩放结果要写到独立的缓冲区。
2. **各级尺寸/格式不同**：转换改格式、缩放改尺寸，每步输出的宽高/bpp/数据都不同，需要独立缓冲。
3. **流水线**：分开后形成清晰的"原始→转换→缩放→显示"数据流，每级只读上一级、写本级。

**内存复用**：tConvertBuf 和 tZoomBuf 都是"首次 malloc，后续复用"，不会每帧分配。

## Q12. 如果我想加一个"图像旋转 90 度"的功能，在你这个架构里怎么加？

**参考答案（考察架构理解 + 扩展能力）：**

按照项目的模块化范式，旋转属于图像几何变换，和 zoom/merge 同类，应该加在 **render 模块**：

1. 在 `render/operation/` 下新建 `rotate.c`，实现 `int PicRotate(PT_PixelDatas src, PT_PixelDatas dst, int angle)`，用最近邻/坐标变换算法。
2. 在 `render.h` 里声明这个函数。
3. 在 `render/operation/Makefile` 的 obj-y 里加上 `rotate.o`，让构建系统编译它。
4. 在 main.c 主循环里，缩放之后、合并之前插入旋转步骤，并更新 `ptVideoBufCur` 游标指向旋转结果缓冲区。

如果要做得更"框架化"，可以像转换器那样，把 render 操作也抽象成带函数指针的接口 + 注册链表，实现可配置的图像处理流水线。但对当前需求，直接加函数最简单。

**关键**：得益于模块化和游标设计，加新功能**不用动采集/显示/转换模块**，只在 render 层和 main 流水线里加一步即可，体现了低耦合。

## Q13. T_PixelDatas 这个结构体为什么这么设计？iLineBytes 和 iWidth*bpp/8 有什么区别？

**参考答案：**

```c
typedef struct PixelDatas{
    int iWidth;       // 宽（像素数）
    int iHeight;      // 高（像素数）
    int iBpp;         // 每像素位数
    int iLineBytes;   // 每行字节数
    int iTotalBytes;  // 总字节数
    unsigned char *aucPixelDatas;  // 数据指针
} T_PixelDatas;
```

它是**全系统统一的图像数据描述符**，采集、转换、缩放、显示都用它传递图像，避免各模块自定义格式，是解耦的基础。

**iLineBytes vs iWidth*bpp/8**：
- 理论上 `iLineBytes = iWidth * iBpp / 8`，本项目代码里也是这么算的。
- 但**单独存 iLineBytes 字段是有意义的**：因为很多硬件（framebuffer、摄像头）的一行会有**对齐填充**，实际行字节数（stride/pitch）可能大于 `width*bpp/8`。比如宽度不是 4 的倍数时，硬件可能按 4 字节对齐补齐。
- 单独存 iLineBytes，寻址时用 `y * iLineBytes` 而不是 `y * width * bpp/8`，能正确处理有填充的情况，更通用健壮。

这是图像编程里 **stride（行跨度）** 的重要概念——很多人会忽略 stride 和 width 的区别导致图像错位/倾斜。

| 模式 | 项目体现 |
|------|---------|
| 策略模式 | T_VideoConvert / T_VideoOpr / T_DispOpr 多种可替换实现 |
